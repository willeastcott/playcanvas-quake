# Visual validation

## Latest resize validation

Live validation on 2026-08-18 loaded the same deterministic E1M1 rocket-impact state in a pinned 320x200 stage and the ordinary 1152x720 stage. Particle depth still selects the source-shaped size in the logical Quake viewport, then that logical size is scaled exactly once into the WebGL framebuffer. At 1152 pixels wide, a two-pixel logical particle therefore occupies seven physical pixels rather than remaining an undersized two pixels or using the chunkier 14-pixel result of re-running the software depth formula at the physical width. Both views retained the same apparent particle scale and the browser reported no error logs.

The same rocket-impact state also exposed that the dedicated particle layer had been appended after PlayCanvas's UI/post-process boundary. Although its material requested depth testing and depth writes, that late backbuffer pass did not share the world's depth attachment. The layer is now inserted immediately before UI, inside the world post-process pass; its live composition order is `World`/`Depth`/`Skybox`/`World`/`Immediate`/`Immediate`/`Quake particles`/`UI`/`Quake viewmodel`. A fresh browser capture changed only the expected particle coverage and reported no errors, while a focused regression prevents the particle layer from crossing the UI boundary again.

Automated tests prove data parsing and selected runtime behavior, but they do not prove visual fidelity. Completion requires direct 320x200 comparisons against a faithful renderer using the same verified PAK.

## Capture procedure

1. Run `npm run prepare:shareware` and confirm the expected PAK digest.
2. Run `npm run dev`.
3. Append `capturePng=1` to the frozen capture URL. The validation-only path pins the stage and WebGL framebuffer to exactly 320x200 with device-pixel ratio 1, independently of the surrounding browser viewport.
4. Wait for the capture-ready frame after the loading overlay disappears.
5. Decode the PNG data URL exposed as the fallback text of `#screen-canvas` to `artifacts/playcanvas/e1m1-spawn.png`. This data is the lossless 320x200 composite of the WebGL view rectangle below the 2D screen compositor, not a browser screenshot.
6. Capture the reference renderer with its viewport at 320x200 and the supplied `.reference/chocolate-quake/app/id1/capture-e1m1.cfg` configuration.
7. Convert the indexed PCX directly to a lossless PNG with `npm run render:pcx -- --pak <pak> --input <pcx> --output <reference.png>`; append source-ordered `--shift r,g,b,percent` arguments when the scene has palette shifts.
8. Run `npm run compare:captures -- --reference <reference.png> --candidate <playcanvas.png> --output-prefix <comparison>` without rescaling. The TypeScript tool reports full-frame, gameplay-view, and HUD MAE/RMSE and writes the side-by-side, 50% overlay, and absolute RGB difference images.
9. Record every discrepancy in the table below before changing scope.

Do not compare a WebGL canvas alone: the HUD, palette shifts, notify text, menu, console, and intermission are composed on the overlaid 2D canvas.

`capturePng=1` is validation-only. It pins `#stage` to the native 320x200 dimensions before PlayCanvas measures the WebGL canvas. After two completed PlayCanvas frames, the app uses nearest-neighbor 2D composition to place `#game-canvas` at the active Quake view rectangle, draws `#screen-canvas` over it, and encodes that exact framebuffer as PNG. Capture mode also lets Web Audio initialization finish in the background, with explicit failure logging, so a suspended browser-host decoder cannot block visual evidence. Normal gameplay URLs still await audio initialization and do not resize the stage, allocate the capture canvas, or encode it. This replaces the earlier element-screenshot workflow, which silently supplied JPEG pixels even when the result was saved with a `.png` extension.

The live `screenshot` command and restored F12 binding reuse that exact 320×200 world-plus-compositor function. Composition is deferred to the next PlayCanvas `frameend`: a direct key-event copy occurs after WebGL has discarded its backbuffer and was caught producing a black world, while the frame-end path preserves the rendered scene. The browser boundary uses lossless PNG rather than WinQuake's PCX writer, but retains the source `quake00` through `quake99` naming sequence and 100-file ceiling. It requests a normal anchor download and also leaves the same PNG data URL in the screen canvas's fallback text with `data-screenshot-name`/`data-screenshot-ready`, so a browser that blocks the asynchronous download does not lose the image. The in-app-browser F12 check produced `artifacts/playcanvas/e1m1-f12-screenshot.png` (69,090 bytes, SHA-256 `0360f67d7b104be42eba3a68b77ffe240f8a1e1b5ffcc627940edb50f872cc0a`) with the PNG signature, exact 320×200 dimensions, 47,798 non-black pixels in the 320×152 gameplay area, and the complete 46,080-byte RGB HUD band; the next press exposed `quake01.png`. This is operational browser evidence, not a native scene-parity comparison.

Chocolate Quake's PCX writer preserves framebuffer indices rather than the shifted display palette. `npm run render:pcx` uses the TypeScript PCX decoder and applies each source integer palette shift in order before gamma, producing either raw RGB or a lossless PNG according to the output extension. The companion PNG codec handles non-interlaced 8-bit RGB/RGBA scanlines and all five PNG row filters; both formats are regression-tested independently.
